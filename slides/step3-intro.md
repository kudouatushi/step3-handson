# Step3 入門

**手を離し、見張り、声をかける**

Claude Code の公式3機能で体験する「監督付き自律」

- Background Session
- Agent View
- Cross Session Messaging

<!-- 発表時間目安: 講義パート約20分 + ハンズオン45分 -->

## Step3 とは — AI との働き方の第3段階

| 段階 | 働き方 | 人間の役割 |
|---|---|---|
| Step1 | AI に聞きながら自分で書く | 全部 |
| Step2 | ペアプロ（1画面で対話しながら書かせる） | 全行レビュー |
| **Step3** | **worker に任せ、検証して取り込む** | **目標と統合判断** |

Step3 のキーワードは **監督付き自律（supervised autonomy）**

- 実装するのは worker（別セッションの Claude Code）
- 人間は「何を作るか」と「取り込んでよいか」だけを判断する

## 3機能の役割マップ

```
        人間
         │ 目標を渡す / 統合判断
         ▼
      manager（対話セッション = 管制塔）
         │                    ▲
         │ ③ 声をかける        │ 完了通知
         │ (SendMessage)      │
         ▼                    │
      worker（← ① 手を離す claude --bg）
         │
         ▼ 成果物はファイルに残る
      reports/ ・ git diff

  ② 見張る: claude agents（全セッションを1画面で監視）
```

3つの機能は **役割の分離** のための道具

## ① Background Session — 手を離す

```bash
claude --bg --name "分析係" "このリポジトリの○○を調べて報告して"
```

- コマンドは**即座に返る**。仕事は裏のセッションで進む
- `claude logs <id>` — 途中経過を見る
- `claude stop <id>` — 止める
- `claude rm <id>` — 一覧から消す（**片付けは rm まで**）

ポイント: 「待っている時間」が消える。複数の worker を同時に走らせられる

## ① の落とし穴 — 権限は起動時に渡す

**bg セッションの権限ダイアログは、誰も押せない。**

```bash
claude --bg --name "w:task-101" \
  --settings '{"crossSessionInbound":"accept","permissions":{"allow":["SendMessage","Write","Edit","Bash"]}}' \
  "<初期プロンプト>"
```

- 許可が足りない worker は、ダイアログ待ちのまま**静かに止まる**
- 逆に言えば `--settings` の許可リストが worker の行動範囲そのもの
- 初めて開くフォルダの **trust 確認も同じ罠**
  → ハンズオンでは最初に対話セッションで trust を済ませる

## ② Agent View — 見張る

```bash
claude agents
```

- マシン上の**全セッション**（対話・bg）が1画面に並ぶ
- 状態（busy / idle / waiting）、経過時間が見える
- セッションの操作（attach・停止など）もここから

ポイント: worker が増えても「今なにが動いているか」を見失わない

## ② の注意 — 状態表示は「目安」

**画面の状態表示を、完了の判定材料にしない。**

- busy / idle は「いま応答を生成しているか」程度の意味
- idle は「終わった」ではない（メッセージ待ちでも idle）
- 完了の判定は、worker が書いた**ファイル**で行う（後述の原則①）

Agent View は「異変に気づく」ための道具。「検収する」ための道具ではない

## ③ Cross Session Messaging — 声をかける

セッション同士が同一マシン内で連絡し合う（Unix ソケット経由）

- **ListAgents** — 今いるセッションの一覧（名前と ref）
- **SendMessage** — 名前を指定してメッセージを送る

```
manager「w:task-101 へ: tasks/task-101.md を実行して」
worker 「manager へ: done task-101」
```

対話セッションに「○○に△△と送って」と日本語で頼めばよい

## ③ の罠 3つ（ハンズオンで全部踏みます）

1. **初回送信は ref を要求されることがある**
   エラー文中の `名前 [ref]` をコピーして再送すれば届く。2回目からは名前だけで OK

2. **success:true は配達証明ではない**
   「送信を受け付けた」だけ。受信許可がない相手には hold され、届かないまま
   期限切れで消えることもある。配達確認は**受信側の挙動**で取る

3. **trust ダイアログ表示中のセッションは一覧に出ない**
   「いない」ように見えて、実は応答待ちで止まっているだけ、がありうる

## 設計原則 — 正はファイル、メッセージは起床合図

Step3 の運用で一番大事な決めごと:

- worker の成果は **reports/ のファイルと git diff** に残す
- 完了通知（SendMessage）は「見に行くきっかけ」にすぎない
- 「テストを追加しました」という**文章を信じない**。
  テストの実行ログと diff で裏を取る

> 通知が届かなくても、ファイルが書けていれば成果は成立する。
> 通知が届いても、ファイルがなければ完了ではない。

## ハンズオン全体像（45分）

ターミナル3枚で進めます:

| ターミナル | 役割 |
|---|---|
| T1 | human — 起動・確認の手作業 |
| T2 | Agent View — 監視画面（出しっぱなし） |
| T3 | manager — 対話 Claude Code（管制塔役） |

| Ex | 内容 | 時間 |
|---|---|---|
| Ex1 | `--bg` で手を離す | 10分 |
| Ex2 | Agent View で見張る | 5分 |
| Ex3 | SendMessage で声をかける（罠を踏む） | 10分 |
| Ex4 | ミニ manager–worker で Step3 一巡 | 20分 |

## Ex1–Ex2: 手を離して、見張る

**Ex1 のゴール**: bg セッションに分析タスクを投げ、`logs` で結果を見る

- 確認ポイント: コマンドがすぐ返る。仕事は裏で進む
- 片付けは `stop` → `rm` まで

**Ex2 のゴール**: Agent View に Ex1 のセッションが現れ、状態が変わるのを見る

- 確認ポイント: 自分が起動していないセッションも見える（マシン全体）
- 状態表示は目安であって検収材料ではない

## Ex3: 声をかける — 罠を体で覚える

**ゴール**: manager（T3）から応答係の bg セッションに送信し、返信を受け取る

確認ポイント:

1. 初回送信の **ref 要求エラー** → ref 付き再送で届く
2. **success:true でも安心しない** — 返信（受信側の挙動）で配達を確認
3. Agent View で、受信した瞬間に相手が動き出すのが見える

## Ex4: ミニ manager–worker — Step3 を一巡

```
あなた ──目標──▶ manager(T3) ──SendMessage──▶ worker(bg)
                                                  │ 実装
あなた ◀─統合判断─ manager ◀──done 通知 + reports/─┘
```

1. git init（裏取りの基準を作る）
2. worker 起動（`--settings` で権限を渡す）
3. manager からタスク仕様のパスを SendMessage
4. done 通知 → **ファイルと diff で裏取り**（manager にやらせ、自分でも見る）
5. 納得したら**自分の手で** git commit（worker はコミットしない）

## 持ち帰ってほしい3原則

1. **正はファイル、メッセージは起床合図**
   完了判定は reports と git diff。通知・画面表示・報告文を判定材料にしない

2. **権限は起動時に渡す**
   bg のダイアログは誰も押せない。`--settings` が worker の行動範囲を決める

3. **manager は実装せず、worker は統合しない**
   役割の分離が、並列化の速度と検証の独立性を両立させる

## 次のステップ

今日の構成は最小形。実運用ではここに載せていく:

- **タスク仕様のテンプレート化** — 完了条件を機械判定できる形で書く
- **manager の権限設計** — 実装系コマンドを deny し「実装しない」を権限でも裏打ち
- **worktree 分離** — worker ごとに作業ツリーを分けて並列化
- **検証の自動化** — 複写ログの突き合わせ、境界侵犯チェック

まずは今日の3コマンド（`--bg` / `agents` / SendMessage）を
**普段の作業に1つ**混ぜるところから
